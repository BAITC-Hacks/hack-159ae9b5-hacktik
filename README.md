# ИЭК — система расчёта потребности в закупках

Веб-платформа для менеджера отдела закупок ТОО «Электрокомплект»: заменяет ручной
свод Excel на расчёт потребности в пополнении склада с объяснимыми рекомендациями
и вспомогательным AI-слоем. Финальное решение всегда принимает менеджер — система
ничего не отправляет поставщику автоматически.

## 1. Описание проекта

Основной сценарий: менеджер выбирает склад/категорию → запускает расчёт →
получает список рекомендаций, сгруппированных по поставщикам, с обоснованием
каждой позиции → может вручную скорректировать количество → подтверждает
заказ → экспортирует его.

## 2. Архитектура

```
Next.js (React + TS) ──REST──> FastAPI ──> Procurement Engine (детерминированный)
                                       └──> AI Gateway (только объяснение, 5 функций)
                                       └──> Data Layer (Excel → позже PostgreSQL)
```

- **Procurement Engine** (`backend/app/procurement_engine.py`) — весь расчёт.
  Не зависит от AI и не делает сетевых вызовов; для одинаковых входных данных
  всегда даёт одинаковый результат.
- **AI Gateway** (`backend/app/ai_gateway.py`) — единственное место, где backend
  обращается к Anthropic API. Получает только уже посчитанные `Recommendation`
  как обычные данные; не имеет доступа к БД, файловой системе или shell.
- **Data Layer** (`backend/app/data_loader.py`) — сейчас генерирует данные,
  повторяющие структуру, описанную в задаче (продажи, остатки, MOQ,
  сезонность). См. раздел 15.

## 4. Запуск backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate

npm run dev
```

Откройте http://localhost:3000

## 6. Структура данных

**⚠️ Реальные Excel-файлы ИЭК не были включены в это задание — платформа сейчас
работает на сгенерированном наборе данных той же структуры** (`data_loader.load_sample_dataset`),
чтобы весь пайплайн (расчёт → API → интерфейс) был рабочим сразу.

Чтобы подключить настоящие файлы:
1. Положить Excel-файлы ИЭК в `backend/data/raw/`.
2. Изучить реальные листы/колонки и заполнить `COLUMN_MAP` в `data_loader.py`.
3. Реализовать `load_from_excel()` (сейчас это размеченный стаб с описанием шагов).
4. Заменить вызов `load_sample_dataset()` на `load_from_excel()` в `main.py`.

Внутренняя модель данных (`SkuInput` / `MonthlySales` в `procurement_engine.py`)
не изменится — именно ради этого данные и код расчёта разделены.

## 7. Алгоритм расчёта

Для каждого SKU, по порядку:

1. **Очистка выбросов** (`_detect_outliers`) — медианное абсолютное отклонение
   (MAD), устойчивое к перекосам от самих выбросов. Разовые крупные заказы и
   концентрация продаж на одном (обезличенном) клиенте понижаются к медиане,
   но не удаляются из истории — только из расчёта обычного спроса.
2. **Компенсация stockout** (`_compensate_stockouts`) — если товара не было на
   складе часть месяца, продажи этого месяца масштабируются на
   `дней_в_месяце / дней_в_наличии`, с ограничением ×2, чтобы не
   экстраполировать слишком агрессивно от коротких периодов.
3. **Тренд** (`_estimate_trend`) — тренд применяется только если рост/спад
   подтверждается несколькими последовательными окнами, а не одним скачком
   между двумя точками (сравнение направления в 3-месячных окнах).
4. **Сезонность** (`_seasonal_index`) — индекс = средний скорректированный
   спрос в данном календарном месяце / средний спрос за всю историю,
   с демпфированием при малом количестве наблюдений.
5. **Итоговый прогноз** = базовый спрос × (1 + тренд) × сезонный индекс.
6. **Рекомендация** = max(0, прогноз − остаток − в пути), округлено вверх до MOQ.
7. **Срочность** — high/medium/low по покрытию остатка в днях относительно
   срока поставки (lead time).

Все промежуточные факторы (тренд, сезонность, исключённые выбросы,
компенсация stockout) сохраняются в `Recommendation.debug` и видны по кнопке
«Подробнее» на странице товара.

## 8. Метод обнаружения выбросов

Modified Z-score на основе MAD (порог 3.5, по Iglewicz & Hoaglin) — выбран
вместо среднего/стандартного отклонения, так как сам выброс искажает эти
показатели. Отдельно проверяется концентрация продаж на одном клиентском
сегменте (>60% месячных продаж от одного анонимного клиента при объёме
существенно выше медианы).

## 9. Метод обработки stockout

См. п.7.2 выше. Метод объясним: в интерфейсе явно указывается, за сколько
месяцев и на сколько был скорректирован спрос.

## 10. Метод учёта сезонности

См. п.7.4. Требует минимум одного наблюдения для целевого календарного
месяца; индекс демпфируется к 1.0 при малом количестве данных, чтобы не
переоценивать сезонность по недостаточной истории.

## 11. Метод учёта тренда

См. п.7.3. Единичный скачок продаж не признаётся трендом — тренд применяется
только при согласованном направлении в нескольких последовательных
3-месячных окнах.

## 12. Как формируется рекомендация

`recommended_quantity = ceil_to_moq(max(0, forecast − stock − in_transit))`,
где `forecast` уже учитывает очистку выбросов, компенсацию stockout, тренд и
сезонность (см. п.7).

## 14. Ограничения AI

AI-слой (`ai_gateway.py`) имеет доступ только к пяти функциям:
`get_product_history`, `get_recommendation`, `explain_recommendation`,
`compare_scenarios`, `suggest_adjustment`. Все они read-only относительно уже
посчитанной рекомендации. AI **не может**: выполнять SQL, менять БД,
подтверждать или отправлять заказ, иметь доступ к файловой системе или shell.
Основной расчёт (`procurement_engine.py`) полностью детерминирован и не
вызывает AI ни на одном этапе.

## 15. Ограничения безопасности

- Клиентские данные, попадающие в AI, уже обезличены на уровне
  `procurement_engine` — идентичность клиента никогда не передаётся дальше,
  только флаг/доля «крупная продажа одному клиенту».
- Все изменения количества менеджером пишутся в audit log
  (`backend/app/audit.py`): пользователь, время, SKU, старое и новое
  количество, действие.
- Интерфейс не содержит технических вкладок (Copilot/Agent/Architecture и
  т.п.) — только «Заказы на закупку», «Поставщики», «Товары», «История
  расчётов», как в обычной системе управления закупками.

## 16. Как протестировать систему

1. Запустить backend и frontend (см. пп. 4–5).
2. На главной странице выбрать склад/категорию (или оставить «Все») и нажать
   «Рассчитать потребность» — расчёт не запускается автоматически при
   открытии страницы.
3. Убедиться, что таблица сгруппирована по поставщикам и для каждой позиции
   есть обоснование.
4. Открыть карточку товара — проверить график истории продаж и нажать
   «Пояснить простыми словами» (нужен `ANTHROPIC_API_KEY`; без ключа
   используется резервное текстовое объяснение из `reasons`).
5. Перейти к подтверждению заказа, изменить количество вручную (поле
   подсветится), подтвердить заказ, экспортировать CSV.
6. Проверить `GET /api/orders/{id}/audit-log` — там должна быть запись о
   ручном изменении.

## 17. Основной принцип

Это не чат-бот, а детерминированная система расчёта закупок с AI как
вспомогательным слоем объяснения. Данные ИЭК → анализ спроса → очистка
аномалий → сезонность/тренд/stockout → остатки и товары в пути → расчёт
потребности → рекомендации → проверка менеджером → корректировка →
подтверждённый заказ.
